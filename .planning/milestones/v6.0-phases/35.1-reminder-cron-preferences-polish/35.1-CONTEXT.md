<decisions>
## Implementation Decisions

### Reminder UI Integration
- **D-01:** Reminders are added inline within the existing event dialog (`event-dialog.tsx`). An "Add reminder" button appends relative/absolute reminder rows. No separate page or modal.
- **D-02:** Smart defaults auto-populate when creating a new event/task/habit/bill reminder. Pre-filled based on source type per REMN-05 defaults (event: 15min/push, task: 1hr/push, habit: 8am/push, bill: 3days/push+email). User can remove or edit before saving.
- **D-03:** Reminder default customization lives in the Settings page, extending the existing Notification Settings section (from Phase 34) with a "Default Reminders" subsection. Shows per-source-type defaults that the user can customize.

### Cron Dispatch Strategy
- **D-04:** Vercel Cron job runs every minute at `app/api/cron/dispatch-reminders/route.ts`. Fetches pending reminders where `fire_at <= now` using `RemindersDB.getPendingReminders()`.
- **D-05:** For each pending reminder, dispatch to all channels (push, email) in parallel. Use existing `sendReminderEmail()` from `lib/email/send.ts` for email. Build a new `sendPushNotification()` in `lib/push/send.ts` using `web-push` and `PushSubscriptionsDB`.
- **D-06:** Failed deliveries get `status='failed'` with error logged. No automatic retry in v1 — keeps the cron simple. Retry can be added in a future phase.
- **D-07:** Cron secured with `CRON_SECRET` header validation, matching the existing `sync-transactions` cron pattern.

### Quiet Hours Enforcement
- **D-08:** Quiet hours enforced at dispatch time in the cron job. Before sending push, check user's `quiet_hours_start`/`quiet_hours_end` from their profile.
- **D-09:** Push notifications during quiet hours keep `status='pending'` and are picked up on the next cron run after quiet hours end. Email is exempt from quiet hours (arrives silently in inbox).
- **D-10:** Quiet hours settings exposed in the Notification Settings section alongside push toggle and reminder defaults.

### Reminder API Routes
- **D-11:** CRUD routes at `app/api/reminders/route.ts` (GET list, POST create) and `app/api/reminders/[id]/route.ts` (PATCH update, DELETE). Follow established API patterns.
- **D-12:** Reminder defaults routes at `app/api/reminder-defaults/route.ts` (GET, PUT upsert). Uses `ReminderDefaultsDB`.
- **D-13:** `fire_at` pre-computed on create (REMN-09). When an event is rescheduled, all associated reminders have `fire_at` recomputed.

### Mobile Responsive Calendar (RESP-01, RESP-02, RESP-03)
- **D-14:** On `sm` breakpoint, calendar sidebar collapses to hidden. A filter/toggle button in `calendar-header.tsx` opens it as an overlay/drawer.
- **D-15:** Mobile defaults to Day view. Swipe left/right navigates between days using touch event handlers on the day view component.
- **D-16:** The "+ New Event" button becomes a fixed bottom-right floating action button (FAB) on mobile. Taps open the event quick-create dialog.

### i18n (I18N-01)
- **D-17:** All calendar and reminder UI strings translated in en, zh, zh-TW. Includes: reminder labels, quiet hours settings, default reminder descriptions, mobile calendar navigation labels, FAB tooltip.

### Claude's Discretion
- Internal structure of the push send utility (`lib/push/send.ts`)
- Touch/swipe implementation approach for mobile day navigation
- FAB component styling and animation
- Cron job error logging format and detail level
- Whether quiet hours comparison uses user timezone or UTC (should use user timezone)
- Reminder row component design within event dialog

</decisions>

- `sendReminderEmail()` — Complete email dispatch with per-source-type templates and locale support

- `reminderCreateSchema` / `reminderUpdateSchema` — Zod validation ready for API routes

- API routes: `createClient()` → `getUser()` → auth check → DB class instantiation → operation → JSON response

- Responsive: Tailwind breakpoints (`sm:`, `md:`, `lg:`) throughout calendar components
