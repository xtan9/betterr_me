# Phase 35.1: Reminder Cron, Preferences & Polish - Research

**Researched:** 2026-04-03

**Confidence:** HIGH

## Summary

Phase 35.1 completes the v6.0 Calendar & Reminder Notifications milestone by building on substantial existing infrastructure from Phases 34 (push) and 35 (email). The core work is: (1) a Vercel Cron job that dispatches pending reminders via push and email, (2) reminder CRUD API routes and inline UI in the event dialog, (3) smart defaults and quiet hours in settings, and (4) mobile-responsive calendar layout with swipe navigation.

The existing codebase already has `RemindersDB`, `ReminderDefaultsDB`, `PushSubscriptionsDB`, `sendReminderEmail()`, VAPID utilities, and the service worker. The `web-push` package (v3.6.7) is installed. What remains is wiring these together: the `sendPushNotification()` utility, the cron route, the reminder API routes, the UI components, and mobile responsive behavior.

**Primary recommendation:** Build bottom-up: push send utility and cron dispatch first (backend complete), then reminder API routes, then UI (event dialog reminders, settings preferences, mobile responsive). This order ensures each layer is testable independently.

### Pattern 2: Push Notification Send Utility
**What:** `sendPushNotification()` using web-push library
**When to use:** Called from cron dispatch for push channel
**Example:**
```typescript
// lib/push/send.ts
import webpush from "web-push";
import { getVapidDetails } from "./vapid";
import { getNotificationUrl } from "./notification-urls";
import { createAdminClient } from "@/lib/supabase/admin";
import { PushSubscriptionsDB } from "@/lib/db";
import type { ReminderSourceType } from "@/lib/db/types";

export interface PushPayload {
  title: string;
  body: string;
  sourceType: ReminderSourceType;
  date?: string;
}

export async function sendPushNotification(
  userId: string,
  payload: PushPayload
): Promise<{ sent: number; failed: number }> {
  const vapid = getVapidDetails();
  webpush.setVapidDetails(vapid.subject, vapid.publicKey, vapid.privateKey);

  const supabase = createAdminClient();
  const pushSubsDB = new PushSubscriptionsDB(supabase);
  const subscriptions = await pushSubsDB.getSubscriptions(userId);

  let sent = 0, failed = 0;
  const url = getNotificationUrl(payload.sourceType, { date: payload.date });

  for (const sub of subscriptions) {
    try {
      await webpush.sendNotification(
        { endpoint: sub.endpoint, keys: { p256dh: sub.p256dh, auth: sub.auth } },
        JSON.stringify({ title: payload.title, body: payload.body, url })
      );
      sent++;
    } catch (err) {
      failed++;
      // If 410 Gone, subscription expired — clean up
      if ((err as { statusCode?: number }).statusCode === 410) {
        await pushSubsDB.deleteSubscription(userId, sub.endpoint);
      }
    }
  }
  return { sent, failed };
}
```

### Pattern 3: Quiet Hours Check
**What:** Compare current time in user's timezone against quiet hours
**When to use:** In cron dispatch before sending push notifications
**Example:**
```typescript
function isInQuietHours(
  quietStart: string | null | undefined,  // "22:00"
  quietEnd: string | null | undefined,    // "07:00"
  userTimezone: string | null             // "America/New_York"
): boolean {
  if (!quietStart || !quietEnd) return false;

  const tz = userTimezone || "UTC";
  const now = new Date();
  // Get current HH:MM in user's timezone
  const formatter = new Intl.DateTimeFormat("en-US", {
    timeZone: tz, hour: "2-digit", minute: "2-digit", hour12: false,
  });
  const currentTime = formatter.format(now); // "22:30"

  // Handle overnight quiet hours (e.g., 22:00 - 07:00)
  if (quietStart > quietEnd) {
    return currentTime >= quietStart || currentTime < quietEnd;
  }
  return currentTime >= quietStart && currentTime < quietEnd;
}
```

### Pattern 4: Touch Swipe for Mobile Day Navigation
**What:** Touch event handlers for swipe left/right
**When to use:** Day view on mobile
**Example:**
```typescript
// Simple swipe detection — no external library needed
function useSwipe(onSwipeLeft: () => void, onSwipeRight: () => void) {
  const touchStart = useRef<{ x: number; y: number } | null>(null);

  const handleTouchStart = useCallback((e: React.TouchEvent) => {
    touchStart.current = { x: e.touches[0].clientX, y: e.touches[0].clientY };
  }, []);

  const handleTouchEnd = useCallback((e: React.TouchEvent) => {
    if (!touchStart.current) return;
    const dx = e.changedTouches[0].clientX - touchStart.current.x;
    const dy = e.changedTouches[0].clientY - touchStart.current.y;

    // Only trigger if horizontal swipe is dominant and exceeds threshold
    if (Math.abs(dx) > 50 && Math.abs(dx) > Math.abs(dy) * 1.5) {
      if (dx > 0) onSwipeRight(); // swipe right = previous day
      else onSwipeLeft();          // swipe left = next day
    }
    touchStart.current = null;
  }, [onSwipeLeft, onSwipeRight]);

  return { onTouchStart: handleTouchStart, onTouchEnd: handleTouchEnd };
}
```

### Anti-Patterns to Avoid
- **Singleton DB clients in API routes:** Always `const supabase = await createClient()` per request
- **UTC for quiet hours:** Must use user's timezone via `Intl.DateTimeFormat` — the profile already stores `timezone`
- **Sending during quiet hours and marking sent:** Quiet-hour-blocked push must remain `status='pending'` so it fires after quiet hours end
- **Editing `components/ui/`:** Never modify shadcn/ui managed files. Build custom components alongside them.

## Common Pitfalls

### Pitfall 1: Vercel Hobby Plan Cron Limitation
**What goes wrong:** Vercel Hobby plan limits cron to once per day. A `* * * * *` (every minute) schedule will fail deployment.
**Why it happens:** Vercel reserves high-frequency cron for Pro/Enterprise plans.
**How to avoid:** Ensure the project is on Vercel Pro plan, or use a daily schedule as fallback (degrades reminder timeliness significantly). Verify plan before configuring `vercel.json`.
**Warning signs:** Deployment error: "Hobby accounts are limited to daily cron jobs."

### Pitfall 2: Quiet Hours Overnight Wrap
**What goes wrong:** Quiet hours like 22:00-07:00 span midnight. A naive `start <= now <= end` check fails.
**Why it happens:** The end time is numerically less than start time when crossing midnight.
**How to avoid:** If `quietStart > quietEnd`, the check is `currentTime >= quietStart OR currentTime < quietEnd`.
**Warning signs:** Notifications firing at 11 PM despite quiet hours set to 10 PM - 7 AM.

### Pitfall 3: Stale fire_at After Event Reschedule
**What goes wrong:** User reschedules event but reminder `fire_at` still points to old time.
**Why it happens:** `fire_at` is pre-computed for cron efficiency. Event update must trigger recomputation.
**How to avoid:** When updating a calendar event's start_date/start_time, fetch all `pending` reminders for that source and recompute `fire_at` for relative reminders. Absolute reminders are unaffected.
**Warning signs:** Reminders firing for original event time after reschedule.

### Pitfall 4: Push to Expired Subscriptions
**What goes wrong:** `web-push.sendNotification()` throws for expired/unsubscribed endpoints.
**Why it happens:** Browser push subscriptions expire or user clears browser data.
**How to avoid:** Catch errors, check for 410 status code, and delete the stale subscription from `push_subscriptions` table.
**Warning signs:** Growing error count in cron logs, same endpoints failing repeatedly.

### Pitfall 5: Cron Processing Same Reminder Twice
**What goes wrong:** If cron runs overlap (function takes > 1 minute), same pending reminder dispatched twice.
**Why it happens:** No locking — both cron invocations query `status='pending'` and see the same row.
**How to avoid:** Update status to `'sending'` (or immediately to `'sent'`) before dispatching. Or use a batch update at the start of the cron run.
**Warning signs:** Users receiving duplicate notifications.

### Pitfall 6: Missing Timezone on Profile
**What goes wrong:** `profile.timezone` is nullable. Quiet hours check defaults to UTC, sending at wrong times.
**Why it happens:** User never set timezone in profile.
**How to avoid:** Fall back to UTC explicitly, or skip quiet hours enforcement when timezone is null (user hasn't configured it, so quiet hours are meaningless).
**Warning signs:** Quiet hours not working for users who haven't set timezone.

### fire_at Computation
```typescript
function computeFireAt(
  reminder: { reminder_type: "relative" | "absolute"; relative_minutes: number | null; absolute_time: string | null },
  eventStart: string // ISO datetime of event start
): string {
  if (reminder.reminder_type === "absolute" && reminder.absolute_time) {
    return reminder.absolute_time;
  }
  if (reminder.reminder_type === "relative" && reminder.relative_minutes != null) {
    const start = new Date(eventStart);
    start.setMinutes(start.getMinutes() - reminder.relative_minutes);
    return start.toISOString();
  }
  throw new Error("Invalid reminder: missing relative_minutes or absolute_time");
}
```

## Open Questions

1. **Vercel Plan Status**
   - What we know: Hobby plan limits cron to once/day. Pro allows every minute.
   - What's unclear: Which plan this project is on.
   - Recommendation: Verify plan. If Hobby, the `* * * * *` schedule will fail deployment. Either upgrade to Pro or use `0 * * * *` (hourly) as degraded fallback. REMN-08 explicitly requires "every minute" so Pro plan is assumed.

2. **Reminder Data for Non-Calendar Sources**
   - What we know: Reminder types support task/habit/bill but event dialog only adds reminders for calendar events.
   - What's unclear: Does this phase need reminder UI for tasks/habits/bills too, or just calendar events + settings defaults?
   - Recommendation: Phase scope is calendar event reminders in the dialog + defaults for all source types in settings. Other source types get reminders via defaults when created, not via custom UI in this phase.

3. **Event Start Time for fire_at with All-Day Events**
   - What we know: All-day events have `start_time = null`. Relative reminders need a reference time.
   - What's unclear: What time to use as anchor for "15 min before" on an all-day event.
   - Recommendation: For all-day events, treat the anchor as midnight (00:00) of the start_date, so "1 day before" fires at midnight the day before, "1 hour before" fires at 11 PM the day before. Alternatively, use the reminder default's absolute time for all-day events.
