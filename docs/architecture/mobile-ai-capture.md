# Issue 13: native AI capture

Approved issue #13 and iOS MVP scope; #12 TestFlight/device delivery is explicitly deferred by the user. Tests use the already approved authenticated command/route boundaries, constrained persistence/ownership/rollback checks and native UI/browser flows.

Use a separate native assistant endpoint with verified Supabase bearer authentication and the existing server-side LLM provider/model configuration and rate limits. It has no web memory, web search, unrelated history or mutation tools. The request includes the current conversation and explicit AI consent. Read only owner tasks/projects and preferences needed for capture. Reject missing/expired credentials; never use a service-role client for native user operations. Keep provider keys server-side and diagnostics free of task/chat/appointment text.

AI starts off. Explain the context disclosure before enabling it; manual tabs always remain available. Bound conversation/request/output sizes and surface service loss/rate limits. Retain an interrupted request's identity for retry, including across app restart, and permit abandoning a proposal without changing the plan.

The model emits validated task/project/child-task or routine capture intentions, or a clarification message. Ambiguous record identity and outcome-complete versus session-end intent require clarification; this slice does not let the model complete or stop work. Existing-record IDs must come from the supplied owner context. The server derives expected versions and exact before/after previews, and assigns proposal/item IDs. New records receive database IDs during acceptance, linked by stable proposal item IDs. Child tasks may reference an existing project or a project addition in the same proposal.

Persist one owner-private proposal per request UUID with a request fingerprint, immutable body, version, expiry, and acceptance state. Retrying the same request returns the existing preview; concurrent generation can only persist one winner. Preview storage makes no task/project/calendar changes. Acceptance locks the proposal and referenced records, rejects stale versions, then invokes shared task/project/routine commands inside one transaction. Any failed item rolls back every mutation and receipt. The model has no arbitrary SQL or generic command escape hatch. Rejecting changes only proposal state.

Apply backend schema and native endpoint before client rollout; roll clients back first and retain proposal receipts/history. Verify malformed output, ownership, stale proposals, parent-child relationships, duplicates, all-or-nothing failure, interrupted requests, service loss/limits, bilingual copy and AI-off/manual operation. Live-gateway, hosted rollout and physical-device evidence must be reported separately from controlled-provider/local tests.
Native JWT route policy: `/api/mobile/assistant` deliberately accepts only a verified Supabase user bearer token through `authenticateNativeRequest`; it does not opt into the web cookie, API-key, MCP or admin credential fallback chain. The authentication route-contract exception names this exact endpoint; behavior tests verify rejection of invalid identity and use of an owner-scoped public client.
